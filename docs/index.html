Benchmarking Efficient Deep Learning Models for Edge AI Deployment

A reproducible CPU harness that measures what actually happens when you compress a neural network for the edge — and reports the three cases where the standard advice quietly fails.

View source on GitHub Technical report Methodology

The problem with "just quantize it"

The standard advice for deploying a model to an edge device is a short list: pick an efficient architecture, quantize to INT8, compile the graph, prune the weights, use an optimized runtime. Every item is individually well-supported. Applied together, the advice is underspecified in ways that matter.

"Quantize to INT8" describes at least four different procedures — dynamic, post-training static, quantization-aware training, and runtime-specific graph quantization — with different accuracy, different file sizes and, in one case, latency that moves in the wrong direction. Published speedups are typically quoted against whatever baseline the author had, at a batch size and thread count that go unstated, on different hardware.

This project fixes one protocol, measures every optimization against the same architecture's own baseline, and reports the results that contradict expectations.

Findings

Three results contradict the standard advice. They are the reason this project exists.

Slower Dynamic INT8 quantization made the model 1.3× slower

Dynamic quantization converts Linear layers but leaves Conv2d in FP32 on this PyTorch build. A convolutional network holds the overwhelming majority of its parameters in convolutions, so the footprint barely moved — while every batch paid added quantize/dequantize work.

The harness detects this condition rather than hiding it: it inspects the build's own dynamic quantization mappings, and when convolutions are excluded the result carries the note that it describes classifier quantization, not model quantization.

No win Unstructured pruning delivered neither compression nor speedup

At 50% sparsity, global magnitude pruning produced a model statistically indistinguishable from FP32 in both size and latency. Three independent reasons:

  • Dense storage ignores zeros. torch.save writes dense tensors; zeroing values changes neither shapes nor file size.
  • Dense kernels ignore sparsity. oneDNN and MKL-DNN convolution paths have no sparsity fast path for arbitrary masks. Measured: 1.01×.
  • Sparse encoding loses below 50%. A float32 value plus an int32 index costs 8 bytes per surviving weight against 4 bytes dense, so break-even is exactly 50% — and row pointers tip it the wrong way there.

Methodology Measurement order produced a 404% error

The first full sequential run reported pruning as 4.16× slower than FP32. That is implausible: pruning leaves dense tensors, so dense kernels must be unaffected.

Re-measuring the same two models interleaved, in opposite orders, gave 1.01×. The 4.16× was drift in machine state over the ~5 minutes of sequential measurement — thermal throttling plus background load. The protocol looked entirely reasonable: warm-up, many iterations, multiple repeats, medians. None of that catches drift between configurations, because each one is internally self-consistent.

The harness now records the coefficient of variation for every cell and flags anything above 15% as unstable in the output tables, and scripts/check_measurement_order.py reproduces the diagnostic.

Works Static INT8 quantization returns 3.1× at 75% smaller

Post-training static quantization, with activation ranges calibrated on held-out validation data, gave the largest speedup of any rung and a ~4× reduction in serialized weight size. QAT recovered accuracy at the cost of a one-time fine-tuning pass.

Stated caveat: FX graph mode performs conv+BN+ReLU fusion automatically, so part of this speedup is fusion, not precision. Both belong in a realistic pipeline, but attributing the whole effect to INT8 would be wrong.

Figures

Every figure is generated by edgebench report from the raw JSON measurement records — never from a live model. A chart can always be traced back to the run that produced it, and any figure can be regenerated on any machine from a results directory alone.

What makes the numbers trustworthy

Most benchmark repositories report one number per configuration from one run on one machine. This one is built around the ways that goes wrong.

Risk How it is handled
Test-set contamination A fixed seeded permutation carves 5,000 images out of the train split for validation. Quantizer calibration draws from that split, never from the test set. The 10,000 test images are measured exactly once per configuration.
Measurement-order artifacts Every cell records its coefficient of variation; tables flag cv > 0.15 as unstable rather than averaging it away. A diagnostic script reproduces the 404% error described above.
Hidden unavailability An optimization that cannot run is recorded as unavailable with its reason, and appears in the results as an explicit gap. It never silently disappears from the matrix.
Unit ambiguity MACs ≠ FLOPs, and the two differ by 2×. One convention is fixed globally (1 MAC = 1 multiply-accumulate, FLOPs = 2 × MACs) and stated in the output itself.
Irreproducible environments Every record embeds CPU model, thread count, PyTorch/NumPy/ONNX Runtime versions, Python version, RAM, OS and git commit.
Fabricated metrics Energy is measured only where a real hardware counter exists (Linux RAPL). On Windows and macOS it reports not measured with the reason, instead of deriving a number from CPU utilisation.

Two protocol decisions worth calling out

Latency is reported across a grid, not as one number. On a CPU the thread count moves latency more than several of the optimizations being compared, so thread count is an explicit axis rather than an ambient condition. Every configuration is measured at 32×32, three batch sizes and two (49× the pixels), at batch sizes 1, 8 and 32, on 1 thread and on all threads.

Both per-iteration and block timing are recorded. Per-iteration timing is what makes the latency distribution visible, but below roughly 0.1 ms the timer itself becomes a material fraction of the measurement. A separate pass times many forwards inside one timer, which is the trustworthy figure at the fast end. Reporting only one of the two would be misleading in one direction or the other.

Engineering notes

Three decisions shaped most of the code, and each one exists because of a failure mode rather than a preference.

The optimization ladder is fault tolerant by construction

Every optimization returns an outcome whose status is one of applied, unavailable or failed, with a machine-readable reason. A missing dependency or an unsupported operator costs one row of the results table, never the run. That property is what makes the negative results reportable: without it, an optimization that fails on your machine simply vanishes, and you report a smaller matrix without noticing.

Each rung also operates on an independent deep copy of the trained model, which makes the ladder order-independent. torch.compile and FX quantization both mutate module graphs in place, so sharing one instance would make results depend on execution order.

Reporting is a pure function of stored results

Records are written to disk the moment they are produced. A sweep that dies at hour three still leaves three hours of usable data, and a figure can always be traced to the measurement behind it. No forward pass is executed to build a chart, so edgebench report regenerates every table and figure on any machine from results/raw/ alone — no model, no dataset, no GPU.

Unmeasurable metrics are reported as unmeasurable

No energy counter means not measured, not an estimate derived from CPU utilisation or TDP. This is a deliberate constraint: a benchmark whose weakest metric is fabricated stops being a benchmark. The same principle governs memory, where the sampling interval is recorded so the reader can judge the precision, and MAC counting, where a failure yields null rather than a guess.

Two bugs worth remembering

  • Scheduler contracts. Wrapping torch.optim.lr_scheduler is a trap: StepLR.step() returns None and is meant to advance once per epoch, while a cosine schedule for this study advances per step. Mixing the two conventions silently decays at the wrong rate. Fixed with a LearningRateSchedule ABC where every schedule returns the rate it applied — and a test that asserts exactly that for every implementation.
  • Quantization namespaces. Recent PyTorch exposes onednn as a quantization engine name while still accepting x86 and fbgemm as qconfig names. Treating them as one namespace meant reporting "static INT8 unavailable" on a machine where it worked perfectly.

Reproduce it

Check what your machine can actually measure before committing hours to a run — this reports which optimizations will apply and which will be recorded as unavailable.

# install (CPU-only PyTorch is the target) pip install torch torchvision --index-url https://download.pytorch.org/whl/cpu pip install -e ".[onnx,dev]" # what does this machine support? edgebench info # validate the whole pipeline offline in minutes, no download edgebench run-all --config configs/offline.yaml # check measurement stability on your hardware python scripts/check_measurement_order.py # the study: 5 architectures x 10 configurations edgebench run-all # regenerate every figure and table from stored records edgebench report --results results

Scope and limitations

Stated plainly, because a benchmark that does not bound its own claims is not useful.

Limitation Consequence
One dataset, one task CIFAR-10 classification. The methodology transfers; the numbers do not.
Uniform training recipe Makes rows comparable and differences attributable, but under-tunes architectures whose preferred recipe differs.
CPU only GPUs and NPUs rank things differently. All measured numbers are CPU-specific.
Block-sequential measurement Configurations are measured in blocks rather than fully interleaved. Close rankings should be treated as unresolved; the Timing column exists to make that judgement possible.
Energy largely unmeasured RAPL is Linux-only. This is the largest gap in the metric set, and energy per inference is arguably the metric that matters most on a battery-limited device.
No structured pruning Correct channel pruning needs dependency-aware surgery across residual adds and concatenations. A wrong implementation is worse than an absent one.
