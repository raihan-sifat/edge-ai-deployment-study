# Benchmarking Efficient Deep Learning Models for Edge AI Deployment

A reproducible CPU benchmarking harness that measures what actually happens when you
compress a neural network for edge deployment — accuracy, latency, throughput, size,
memory, and the accuracy you lose in exchange.

This is a **research project with working code**, not a paper. Every number is
reproducible from a single command, and every result is traceable to the run that
produced it.

```
                    accuracy   latency   weights   speedup
fp32                  94.31%    18.07 ms   42.70 MiB    1.00x
static_int8           93.12%     5.75 ms   10.78 MiB    3.12x
qat_int8              91.58%     5.34 ms   10.78 MiB    3.35x
dynamic_int8          94.11%    23.30 ms   42.68 MiB    0.77x   <- slower
prune_unstructured_50 93.87%    17.95 ms   42.70 MiB    1.01x   <- no size win
```

_(Illustrative shape of the results. Real numbers depend on your hardware and are
generated by the harness — see [Running the study](#running-the-study).)_

## Why this project exists

"Just quantize the model" is the standard advice for edge deployment. It is also
almost meaningless. There are at least four things people mean by it, and they
produce different accuracy, different file sizes, and different latency — sometimes
in opposite directions.

This harness measures all of them under one protocol and reports where the advice
holds and where it quietly fails. The most useful results are the negative ones:

- **Dynamic INT8 quantization made the model slower** (0.77x) while barely reducing
  its size. It quantizes the classifier head, which holds a tiny fraction of the
  parameters, and leaves every convolution in FP32 while adding per-batch
  quantize/dequantize work. This is the single most common real-world surprise.
- **Magnitude pruning produced no size reduction and no speedup.** `torch.save` writes
  dense tensors regardless of how many zeros are in them, and dense CPU kernels have
  no sparsity fast path. At exactly 50% sparsity, storing values plus indices sparsely
  is _larger_ than dense storage, not smaller.
- **`torch.compile` was unavailable** on the test machine, and saying so is more
  useful than hiding it.

## What makes the results trustworthy

Most benchmark repositories report one number per configuration from one run on one
machine. This one is built around the ways that goes wrong:

| Risk                            | How it is handled                                                                                                                                                                                                          |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Test-set contamination**      | Model selection uses a 5,000-image carve-out of the train split. The 10,000-image test split is used exactly once per configuration, for the reported number.                                                              |
| **Measurement-order artifacts** | A faulty sequential run showed pruning as 4.2x _slower_; interleaved re-measurement showed 1.01x. Every cell records its coefficient of variation, and unstable cells are flagged in the tables rather than averaged away. |
| **Hidden unavailability**       | When an optimization cannot run (no Triton, no backend, unsupported op) it is recorded as `unavailable` with the reason, and appears in the results as an explicit `-`. It never silently disappears.                      |
| **Unit mismatch**               | MACs ≠ FLOPs. One convention (1 MAC = 1 multiply-accumulate, FLOPs = 2 × MACs) is fixed globally and stated in the output.                                                                                                 |
| **Unreproducible environments** | Every record embeds the CPU model, thread count, PyTorch version, OS, and git commit.                                                                                                                                      |
| **Fabricated metrics**          | Energy is measured only where a real hardware counter exists (Linux RAPL). On Windows and macOS it reports `not measured` with the reason, instead of deriving a fake number from CPU utilisation.                         |

## Hardware and protocol

Latency on a CPU is meaningless without stating the thread count, because the thread
count moves latency more than most of the optimizations being measured. Everything is
reported on a grid rather than a single figure:

- **Resolution:** 32×32, the training resolution. 224×224 is supported but not published:
  at batch 32 it costs a measured 10.1 s per ResNet-18 forward pass, which puts one cell
  pair near 14 hours across ten rungs. Stems here are also re-engineered for 32×32, so
  224×224 would partly measure the adaptation rather than the input size.
- **Batch sizes:** 1, 8, 32 — batch 1 is the realistic edge serving case.
- **Thread counts:** 1 and all available — 1 thread is the honest proxy for a small
  edge core and cannot be bought back with more hardware.

Headline numbers use **batch 1, single thread, 32×32**: the least flattering
configuration available.

## Running the study

```bash
git clone https://github.com/raihan-sifat/edge-ai-deployment-study
cd edge-ai-deployment-study

python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # Linux / macOS

# CPU-only PyTorch is what this study targets
pip install torch torchvision --index-url https://download.pytorch.org/whl/cpu
pip install -e ".[onnx,dev]"
```

Check what your machine can actually measure before committing hours to a run:

```bash
edgebench info
```

```
  Edge AI Deployment Study
  ----------------------------------------------------------
  CPU                  12th Gen Intel(R) Core(TM) i5-12450H
  Logical cores        12
  PyTorch              2.14.0+cpu
  Quantization engine  onednn

  Energy metering      unavailable (no per-package energy counter)

  Optimization ladder
    [x] fp32
    [x] compile
    [x] dynamic_int8
    ...
```

Then run it:

```bash
# One model, full pipeline, with figures and tables
edgebench run-all --models resnet18

# The full study: all 5 architectures, whole ladder
edgebench run-all

# No internet? Validate the whole pipeline on synthetic data in minutes
edgebench run-all --config configs/offline.yaml
```

### Commands

| Command             | Purpose                                                               |
| ------------------- | --------------------------------------------------------------------- |
| `edgebench info`    | Report the environment and which optimizations will apply here        |
| `edgebench train`   | Train and checkpoint the models                                       |
| `edgebench run-all` | Train or load, apply the ladder, measure everything, build the report |
| `edgebench report`  | Regenerate figures and tables from stored records (no retraining)     |

Any config value can be overridden without editing files:

```bash
edgebench run-all --set train.epochs=5 --set benchmark.repeats=3
```

## What is measured

Five architectures across ten configurations of the optimization ladder.

**Models** — all trained from scratch under an identical recipe, with the
ImageNet stem adapted for 32×32 inputs (stride-1 3×3 conv, no max-pool). No
pretrained weights are used: every number is attributable to the architecture and
the recipe, not to ImageNet transfer.

| Model             | Role                                                         |
| ----------------- | ------------------------------------------------------------ |
| ResNet-18         | Accuracy/throughput reference baseline                       |
| MobileNetV2       | Inverted residuals, depthwise separable, ReLU6               |
| MobileNetV3-Small | Squeeze-and-excitation and hard-swish; smallest in the study |
| ShuffleNetV2-x1.0 | Channel shuffle, ARM-friendly                                |
| EfficientNet-B0   | Compound-scaled; largest in the study                        |

**Optimization ladder**

| Stage                   | What it does                                                         |
| ----------------------- | -------------------------------------------------------------------- |
| `fp32`                  | Eager PyTorch reference                                              |
| `compile`               | `torch.compile` (Inductor), with cold-start cost recorded separately |
| `dynamic_int8`          | Weights quantized ahead of time, activations per batch               |
| `static_int8`           | FX graph-mode PTQ with activation ranges from calibration            |
| `qat_int8`              | Quantization-aware fine-tuning, then convert                         |
| `prune_unstructured_50` | Global magnitude pruning, masks made permanent                       |
| `onnxruntime`           | ONNX export + ONNX Runtime, a different runtime entirely             |
| `onnxruntime_int8`      | ONNX Runtime's own dynamic quantization                              |

### Metrics

- **Accuracy** — top-1, top-5, loss, and **expected calibration error**. ECE matters
  because deployments gate on confidence thresholds: a quantized model can hold its
  top-1 score while becoming badly overconfident.
- **Per-class accuracy** — aggregate top-1 hides a model that collapses on one or two
  classes, which is usually unacceptable in practice.
- **Latency** — p50/p90/p95/p99, plus per-iteration and block-timed figures. Raw
  samples are stored so distributions can be plotted.
- **Throughput** — images/second, from the median.
- **Footprint** — serialized weight bytes (what ships), parameter breakdown,
  MACs, and peak RSS delta (what competes for RAM with everything else).
- **Energy** — joules per inference and per sample, where a hardware counter exists.

│   ├── batch_scaling.png
│   └── per_class_accuracy.png             # where quantization hurts
├── tables/
│   ├── main_comparison.md                 # paste-ready comparison
│   ├── frontier.md                        # only non-dominated configurations

│   └── environment.md
└── raw/

Reporting reads **only** the JSON records. No forward pass is executed to build a
chart, so figures can be regenerated on any machine from a results directory produced
elsewhere:

```bash
edgebench report --results results
```

## Tech stack

Everything runs on commodity **CPU-only** hardware — no GPU, no cloud, no paid
services. The stack is deliberately small so the harness installs and reproduces on
a laptop.

| Layer                         | Tools                                                                                                                                                                                    |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Language & runtime**        | Python 3.10–3.12 (`requires-python = ">=3.10"`), Node.js ESM (portfolio validation only)                                                                                                 |
| **Deep learning**             | PyTorch ≥2.2 (CPU wheels), torchvision ≥0.17, CIFAR-10                                                                                                                                   |
| **Optimization & deployment** | `torch.compile` (Inductor), PyTorch quantization (dynamic INT8, FX graph-mode static PTQ, QAT; `onednn` backend), global magnitude unstructured pruning, ONNX ≥1.15 + ONNX Runtime ≥1.17 |
| **Numerics & data**           | NumPy ≥1.24, pandas ≥2.0, PyYAML ≥6.0 (strict typed config)                                                                                                                              |
| **Measurement**               | Custom latency protocol (p50–p99 + CV), `psutil` for peak RSS, MAC counting, Linux RAPL for energy                                                                                       |
| **Reporting & figures**       | Matplotlib ≥3.8, Pillow (WebP export), Markdown/CSV table writers, stdlib Markdown→HTML renderer with optional Pandoc + LaTeX                                                            |
| **CLI & tooling**             | Typer ≥0.12, `tqdm`, `setuptools` (editable install), `edgebench` console script                                                                                                         |
| **Quality & CI**              | `pytest` + `pytest-cov`, Ruff (lint + format), `pre-commit`, GitHub Actions (Python 3.10/3.11/3.12 matrix, offline smoke pipeline, real-data path)                                       |
| **Portfolio & docs**          | MDX + self-contained CSS (Astro/Next.js compatible), `@mdx-js/mdx` + `remark-frontmatter` / `remark-mdx-frontmatter` for validation, BibTeX (`references.bib`)                           |

A few notes on the choices:

- **CPU-only PyTorch** keeps the numbers honest for an edge target and makes the
  whole study runnable without special hardware.
- **ONNX and ONNX Runtime are optional.** If they fail to install the harness degrades
  gracefully and records the optimization as `unavailable` rather than crashing.
- **Energy metering uses RAPL** where a real hardware counter exists (Linux). On
  Windows and macOS it reports `not measured` instead of inventing a number.
- **The portfolio assets are framework-agnostic** — plain MDX and CSS that drop into
  an existing Astro or Next.js site, with no Tailwind or component library required.

## Portfolio case study

`portfolio/` holds a drop-in case study page for an existing portfolio site (Astro
or Next.js), along with the figures and metrics it renders from.

```bash
edgebench run-all                              # produce real results first
python scripts/export_portfolio_assets.py      # generate images/ and data/
```

The page renders entirely from `portfolio/data/results.json` — no hardcoded
numbers, so it cannot drift from the results. If the results came from the
synthetic offline config, the export sets `provisional: true` and the page renders
a visible warning rather than presenting placeholder accuracy as a measurement.

`portfolio/README.md` covers installation for both frameworks. Note that
**Next.js needs `remark-frontmatter` and `remark-mdx-frontmatter`**: without them
the build still succeeds but the page renders its own YAML as body text, because
`---` parses as a thematic break. `scripts/validate_case_study.mjs` detects this
and runs in CI.

## Design notes

Three decisions shaped most of the code.

**The optimization ladder is fault tolerant by construction.** Every optimization
returns an outcome with `status ∈ {applied, unavailable, failed}` and a reason. A
missing dependency or an unsupported operator costs one row of the results table,
never the run. This is what makes the negative results reportable instead of
invisible.

**Reporting is a pure function of stored results.** Records are written to disk the
moment they are produced, so a sweep that dies at hour three still leaves three
hours of usable data, and a figure can always be traced to its source measurement.

**Unmeasurable metrics are reported as unmeasurable.** No energy counter means
`not measured`, not an estimate. This is a deliberate constraint: a benchmark whose
weakest metric is fabricated stops being a benchmark.

## Reproducing the negative result about measurement order

While developing this harness, a full sequential run reported 50%-pruned ResNet-18
as **4.2x slower** than FP32 — implausible, since pruning leaves dense tensors.
The diagnostic in `scripts/` re-measures the same two models in opposite orders:

```bash
python scripts/check_measurement_order.py
```

```
fp32       median=  18.07 ms  min= 17.24  max= 18.14  spread= 0.90 ms
prune50    median=  18.17 ms  min= 17.95  max= 19.00  spread= 1.05 ms

prune50 / fp32 median ratio: 1.01x
between-configuration effect: 1.01x
within-configuration spread : 5.8% of median
```

The 4.2x gap was measurement-order drift, not a property of pruning. Every table now
carries a `Timing` column flagging cells whose CV exceeds 15%.
